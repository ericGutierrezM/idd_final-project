DATAOPS LIFECYCLE
7
• Development
• In DataOps, the step may involve building a new pipeline, changing a data model or redesigning a dashboard.
• Example: We add a new weather/promotionspipeline.
• Testing
• Usually testing includes testing of inputs, outputs and business logic
• These tests should be performed at each stage of the data analytics pipeline, to ensure that results of the particular data job meet expectations.
• Example: We validate weather structure, schema, contents, data logic.
• Deployment
• This presumes moving data jobs between environments, pushing them to the next stage, or deploying the entire pipeline in production.
• Many times, given that Production data is not allowed in other environmentsthan PROD, it may be the case that data is pushed in each environmentseparately.
• Example: We move pipeline into the production environment,by passing from DEV to QA to PREPROD and finally to PROD.
• Monitoring
• A must have to ensure data quality,monitoring allows data professionalsto identify bottlenecks, catch abnormal patterns, and measure adoption of changes.
• Monitoring often relies on AI-driven anomaly detection algorithms.
• Example: We check data arrives when scheduled and with the right data quality checks in place.
• Orchestration
• In the data world, orchestration automates moving data between different stages, monitoring progress, triggering autoscaling, and other operations related to the
managementof data flows.
• It covers each stage and the end-to-end data analytics pipeline.
• Example: Yourchoice orchestrator (Airflow or Azure Data Factory or AWS Step Functions) triggers everything.

DATAOPS WORKING SESSION – 35’
9
Goal: Your Forecasting Model Is Going Live
Time: 15 minutes
Work in small teams -> 20 mins to share ideas
Scenario:
Monday, 4am. The forecasting engine is about to run. Several data issues have been detected. Your team is 
responsible for deciding what to do.
Your Task  - Split into 5 groups, each group will discuss one question and prepare a 2-minute answer.
• Group 1: Weather data is missing. Should the forecast run? What checks should be in place? Who should be 
alerted?
• Group 2: Promotions data contain 0 rows. How do you detect the issue? Should the forecast continue? 
What is the business impact?
• Group 3: The Shipments file arrived, but a column name changed. The pipeline fails. How can 
DataOps prevent this? What controls would you implement?
• Group 4: The data usually arrives at 2 AM. Today it arrives at 6 AM. The forecast is scheduled for 
4 AM.
What should happen? Should the forecast wait? Should it run? How would you automate the decision?
• Group 5:The data arrives successfully, however, volumes suddenly increase by 300%.
No errors are reported. How would you detect this? How would you distinguish a true business event 
from a data quality issue?

--- PAGE 10 ---
DATAOPS WORKING SESSION – PROPOSED SOLUTION
10
Group Incident Proposed Solution
Group 1 Missing Data— Weather dataset did not arrive
Add data freshness checksand dependency validation before the forecast runs. If weather 
is mandatory, stop the run and alert Data Engineering / Forecasting Support. If it is optional, 
use an approved fallback such as last available weather or historical averages.
Group 2 Empty Dataset— Promotions table contains 0 rows
Add row count validationand business rules. If promotions are expected for the 
market/week, the pipeline should fail fast, block forecast publication, and alert the data 
owner.
Group 3 Schema Change— Shipments file arrived but a 
column name changed
Implement schema validationand data contracts. The pipeline should check column 
names, data types, mandatory fields, and expected formats before transformation starts.
Group 4 Late Data Arrival— Data usually arrives at 2 AM but 
arrives at 6 AM
Use dependency-based orchestrationinstead of only time-based scheduling. The forecast 
should wait until required data is ready, with a defined timeout and escalation process.
Group 5 Suspicious Data— Volumes suddenly increase by 
300%
Add anomaly detection and volume threshold checkscomparing current data with 
historical patterns. If the increase is abnormal, trigger manual review before allowing the 
forecast to continue.

Your team is responsible for investigating the problem.

Group 2: Customer behavior has changed because of a market event, inflation, new competitors, or a major promotion

Group 3: A new feature engineering release was deployed one month ago
Questions: How would you determine whether the new release caused the issue? What versioning controls should be in place? 
Group 4: The model continues to run successfully every week.
Questions: What KPIs would you monitor? What thresholds would trigger an alert? 
Group 5: The model was trained six months ago
Questions: How often should retraining occur? Should retraining be time -based or performance -based?

--- PAGE 20 ---
MLOPS WORKING SESSION – PROPOSED SOLUTION
20
Group Incident Proposed Solution
Group 1 Data Drift– Customer purchasing patterns have changed 
significantly compared to the data used for training.
Monitor feature distributions and compare production data with training data. Use drift 
detection metrics and dashboards. If significant drift is detected, investigate the cause 
and consider retraining the model.
Group 2
Concept Drift– Customer behavior changed due to 
inflation, new competitors, or changes in promotion 
strategy.
Monitor forecast accuracy and bias over time. Even if input data looks similar, 
relationships between inputs and demand may have changed. Retrain, recalibrate, or 
redesign the model when performance deteriorates.
Group 3 Code & Feature Engineering Changes– A new feature 
engineering release was deployed one month ago.
Use Git versioning, model registries, experiment tracking, and CI/CD pipelines. 
Compare model performance before and after the release and rollback if the 
degradation is linked to the new code version.
Group 4 Monitoring & Alerting– The model continues to run 
successfully every week.
Monitor forecast accuracy, bias, drift metrics, runtime failures, missing predictions, and 
business KPIs. Define thresholds that automatically trigger alerts and investigations.
Group 5 Retraining Strategy– The model was trained six months 
ago.
Establish retraining policies based on time (e.g., monthly), performance thresholds 
(accuracy below target), or drift detection. Validate new models before deployment and 
keep the ability to rollback to previous versions.
